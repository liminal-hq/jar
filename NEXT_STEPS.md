# Next steps for an implementing agent

This repository is no longer a bare structural scaffold: the Rust core, the plugin, and the fish/aquarium frontend path are real, working, and build clean end-to-end (`bun run build`, `cargo fmt --check`, `cargo clippy -D warnings` all pass as of this commit). What's left is mostly gecko/terrarium mode, asset polish, and tests. Read this file first, then the docs it points to, before writing code.

## Reading order

1. `SPEC.md` + `SCREENS.md` — product behaviour and window inventory. Authoritative for everything except rendering/physics/AI and the sim-core implementation.
2. `docs/architecture/3d-engine.md` — rendering stack, coordinate system, steering/AI, physics, 3D models, particles, asset pipeline. Authoritative for anything render/physics/3D.
3. `docs/architecture/rust-core.md` — the Rust simulation core's scope, schema, module breakdown, and its wire contract with the frontend. Authoritative for sim-tick logic and the Rust/JS boundary.
4. `AGENTS.md` / `CLAUDE.md` — conventions (Canadian English, commit format, licence headers, Tauri v2 pitfalls).
5. `docs/ui-mockups/` — the original Claude Design prototype. Reference only, per `docs/architecture/3d-engine.md` §0 — do not port or adapt its code.

## What's real vs. stubbed

**Real, tested, and safe to build on:**

- `crates/jar-protocol` — the full `Critter`/`JarSettings`/`SimEvent`/`SnapshotView` schema, with working `ts-rs` codegen. Run `cargo test -p jar-protocol` after changing any type here; generated TS lands in `apps/jar/src/domain/protocol/generated/` automatically (see `.cargo/config.toml`).
- `crates/jar-core` — a working (if simplified) implementation of aging, mood/energy drift, breeding, genetics, passing, the jar clock, and snapshot save/load, with passing unit tests. Re-check every formula against `SPEC.md` §5 before trusting it (some constants, e.g. the mood-drift smoothing factor and breeding-probability curve, were reasonable placeholders, not values derived from the original prototype).
- `plugins/tauri-plugin-jar` — a working native adapter: background tick loop (unaffected by webview visibility), `Channel<SimEvent>` push, periodic + shutdown-flush autosave, Tauri v2 permissions (autogenerated — don't hand-edit `permissions/autogenerated/`). `get_snapshot` returns a real `SnapshotView`; the command surface is functional.
- `apps/jar/src-tauri` — compiles and links against the plugin, `tauri-plugin-window-state`, and `tauri-plugin-os`. All four windows (`tank`, `critter-card`, `family-tree`, `setup`) are declared in capabilities; the satellite three are opened at runtime from the frontend (`domain/windows.ts`), not pre-declared in `tauri.conf.json`.
- `apps/jar/src/domain/jarClient.ts` — the typed façade is implemented: a zustand store (`useJarStore`) holding `critters`/`settings`/`simSeconds`, merge-not-overwrite on `TickUpdate` (only stats fields change; steering/physics-owned fields are never in the store), the tank-window-owns-the-channel + `jar://event` rebroadcast pattern so satellite windows stay in sync (see the file's header comment for why — each `WebviewWindow` is a separate JS realm and the plugin only supports one live `Channel`), and a `jar` object wrapping every typed command.
- `apps/jar/src/render/` fish path — `steering/` (Yuka `Vehicle` + Wander/Separation/Arrive, a registry-based `SteeringSystem` doing one non-prioritized `useFrame` per frame — see that file's header on the R3F v8 manual-render-takeover pitfall it avoids), `physics/coordinates.ts` (sim-percent ↔ world-unit mapping), `models/FishModel.tsx` (procedural fish: primitive body, one-segment tail-pivot spine-wave approximation, hue/sex/spot dimorphism, life-stage scale), `tank/Fish.tsx` (RigidBody + steering + model + arrive-mode roll + click-to-select), `tank/CrittersLayer.tsx`, `particles/Bubbles.tsx` (rising bubble particles, sum-of-sines drift — flagged in its header as a placeholder for real noise), `environment/AquariumEnvironment.tsx` (floor + fixed containment colliders), and `tank/TankScene.tsx` (wires `Physics` → `SteeringSystem` → environment + critters + conditional bubbles). This is the "one fish rendering and moving, ticking without snapping" milestone the previous version of this file called out as the first target — it's done.
- All four window components (`windows/{Tank,CritterCard,FamilyTree,Setup}/*.tsx`) are wired to real state: Tank renders the drawer/toasts/status chip and the R3F canvas; CritterCard listens for selection events and shows editable name + stats + genetics/lineage; FamilyTree groups by generation with clickable, passed-aware entries; Setup exposes every toggle/slider/select and an add-critter button.
- `apps/jar/src/theme/theme.ts`, `components/{StatBar,Toast,Drawer}.tsx`, `domain/{windows,selection,simConstants}.ts` — all real.

**Stubs / gaps — this is the real remaining work:**

- **Gecko/terrarium mode has no rendering path.** `render/environment/TerrariumEnvironment.tsx` is still a single flat-coloured box (per `docs/architecture/3d-engine.md` §8.2 it needs substrate/mossy wall/branch collider/foliage/heat-lamp glow), and there is no gecko equivalent of `models/FishModel.tsx` or `tank/Fish.tsx` (climbing/perching steering behaviour is unspecified beyond `docs/architecture/3d-engine.md`'s notes). `TankScene.tsx` only ever mounts the aquarium path today — wiring `settings.mode === 'Gecko'` to a terrarium scene is unstarted.
- **`render/effects/` is still just a `.stub.ts` marker.** The CRT/neon post-process pass for the `NeonCrt` tank frame (`@react-three/postprocessing` is already a dependency) isn't implemented. Delete the marker once real code lands.
- **No mist particle system** (the terrarium counterpart to `Bubbles.tsx`) — `Setup`'s toggle already relabels to "Mist" in gecko mode, but nothing renders it yet.
- **No GLTF asset pipeline in use.** Both fish and (once built) gecko models are primitives; `assets/models/` is empty and `docs/architecture/3d-engine.md` §12's pipeline hasn't been exercised.
- **Theme variants aren't wired.** `jar.setTheme` always sends a theme's default variant name — the per-theme variant row from `SPEC.md` §4 has no UI yet.
- **Per-theme shell surfaces are only partly built.** `DialogShell` applies each theme's background/ink/radius/shadow/accent tokens and (Classic 98/Paper notebook/Handheld LCD) title chrome, but the deeper per-theme surface treatments — Paper notebook's ruled texture, Classic 98's bevel and square control geometry, Neon terminal's glow border, and a themed window-chrome layer so the shadow/glow tokens are actually visible against these non-transparent OS-decorated windows — aren't built. Pair with the theme-variants work above.
- **No frontend tests.** `apps/jar/src/test/` is still empty; `bun run test:js` currently exits non-zero with "no test files found." Writing even a handful of unit tests (e.g. `jarClient`'s merge-not-overwrite logic, `simConstants`'s life-stage boundaries) would let `bun run validate` actually gate something on the JS side.
- **`scripts/`** — only the protocol-bindings regen script exists; no dev/build convenience scripts (e.g. an Android dev-build helper) yet.

## Known gaps worth flagging before you start

- **No fluid/current simulation decision.** Both architecture docs explicitly leave this open (mentioned in `docs/architecture/rust-core.md` §1/§8) — resolve it as a real design decision before building bubble/wake interactions beyond the current cosmetic drift, not by default.
- **Mobile companion sync is unspecified.** `SPEC.md`'s Android companion section says "TBD" for the sync mechanism; `docs/architecture/rust-core.md` §8 confirms this doc doesn't narrow it either.
- **`jar-core`'s formulas are a first pass**, not a transcription of any prior working implementation (there is no prior working implementation — the original prototype's code is explicitly not a porting source, per `docs/architecture/3d-engine.md` §0). Validate mood/breeding numbers against actual play-testing now that critters render and move.
- **No CI has actually run** — `.github/workflows/ci.yml`/`release.yml` are written to the conventions in `AGENTS.md` but have never executed against this repo. Push and confirm before relying on them as a merge gate.
- **The cross-window sync pattern is a deliberate simplification.** Only the tank window holds a live `Channel`; it rebroadcasts every event via a plain Tauri app event so satellite windows stay current. This is documented in `jarClient.ts`'s header as a known limitation (e.g. an event that lands in the gap between a satellite window opening and its `get_snapshot` hydration completing could theoretically be missed) rather than something to silently work around — read that comment before changing the window-open flow.
